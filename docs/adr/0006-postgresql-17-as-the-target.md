# ADR-0006: PostgreSQL 17 is the target database

- **Status:** Accepted
- **Date:** 2026-10-19
- **Deciders:** Davin Akmal Yasha

## Context

The current database is MySQL 9.6 with 98 tables, 1 345 columns, 338 indexes, 161
foreign keys, 44 ENUM columns, 59 JSON columns and 100 DECIMAL columns (82 of them
`decimal(24,2)` money).

The rewrite moves it to PostgreSQL 17. The choice is forced by the Go port, but the
*details* of the move are where the risk lives.

## Decision

**PostgreSQL 17** for the new system. MySQL 9.6 remains, owned by the legacy
application, for the duration of the transition (ADR-0017, ADR-0018).

The conversion preserves:

- **`numeric(24,2)` for money.** Not `bigint`. The `Money` docblock cites
  "human-readable in a SQL client" as a reason for the current design, and PostgreSQL's
  `numeric` is exact base-10, so `SUM()` over the ledger is exact.
- **The 82 money columns' widths**, unchanged.
- **`timestamptz`** for the 251 `timestamp` columns.
- **`GENERATED BY DEFAULT AS IDENTITY`** for the 90 `AUTO_INCREMENT` columns.
- **`boolean`** for the 24 `tinyint(1)` columns.
- **`jsonb`** for the 59 JSON columns.

The 160 `->after()` calls are dropped — PostgreSQL has no column order, so they are pure
noise. The 50 `MODIFY/CHANGE COLUMN` and 47 `DB::statement` calls are translated
explicitly. The 3 `->change()` calls are translated. The 4 `unsigned` columns become
`bigint` with a `CHECK (col >= 0)`.

## Consequences

### Positive

- **Partial indexes** (PostgreSQL-only) for the hot money queries —
  `project_payment_termins (project_id) WHERE status NOT IN ('paid','void')` is
  impossible in MySQL without a generated column.
- **`pg_advisory_lock`** fixes the multi-replica `migrate --force` race in three lines
  (AGENTS.md trap 13).
- **`jsonb` + GIN** makes the 9 `whereJsonContains` sites index-supported. The
  `published_bidding_roles` pivot table (which the performance audit already recommended)
  is still the right fix, and it is available in either engine.
- **`ON CONFLICT (cols) DO NOTHING RETURNING id`** makes the ledger's double-charge
  guard atomic in one statement (ADR-0020).
- **A better planner** for the aggregate queries over the ledger.
- **A cheaper option exists** — PostgreSQL's `numeric` needs no application-side
  conversion, and Go's `int64` minor units are the in-memory representation either way.

### Negative

- **The case-sensitivity change is the single largest silent-breakage risk in the
  entire rewrite.** MySQL's default collation is **case-insensitive**; PostgreSQL's is
  **case-sensitive**. That breaks `WHERE email = ?`, `WHERE token = ?`,
  `WHERE share_token = ?` and every unique index on a human-typed string — i.e. login,
  every Sanctum token lookup, the public brief link, and the firm invite codes. No type
  checker will catch it. It is mitigated by a per-column-family decision (ADR-0008), not
  by care.
- **The 219 MySQL migrations must be translated**, not just replayed. 21 of them contain
  raw `DB::statement` calls.
- **Two database engines run side by side** for ~20 weeks, with a type-mapping surface
  between them (ETL, ADR-0017).
- **`ON UPDATE CURRENT_TIMESTAMP` does not exist** — and neither does the need
  for a trigger. (Corrected 2026-10-21: the audit measured **ZERO** such
  columns. The legacy schema has no auto-updating timestamp at all: `updated_at`
  is written by Eloquent, and the only `DEFAULT CURRENT_TIMESTAMP` in the
  database is `failed_jobs.failed_at`. The 250-column figure this ADR originally
  carried was never measured. The columns still need a type, not a trigger.)
  trigger or an explicit write.

### Neutral

- The 30 no-op migration stubs are **deleted**, not translated (ADR of the schema work,
  W1 D8). Carrying them forward would carry a lie forward.
- The 44 ENUM columns become native PostgreSQL enums (ADR-0007).

## Alternatives considered

| Alternative | Why not |
|---|---|
| **Stay on MySQL** | Keeps the ENUM trap (`MODIFY COLUMN` is an `ALGORITHM=COPY` table rebuild), the error-1553 trap, no partial indexes, no advisory locks, and `ON CONFLICT` has no explicit-target form. It also keeps the Go port unpleasant. |
| **MySQL 8 instead of 9.6** | The current CI tests 8.0 while production is 9.6. The rewrite uses 9.6 in CI to match production, and PostgreSQL 17 for the new system. |
| **PostgreSQL 18 (if/when released)** | PostgreSQL 17 is the current stable. Taking an unreleased major for a production financial system is not a trade worth making for features the system does not use. |
