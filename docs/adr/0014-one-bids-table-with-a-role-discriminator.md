# ADR-0014: One `bids` table with a role discriminator

- **Status:** Accepted
- **Date:** 2026-10-19
- **Deciders:** Davin Akmal Yasha

## Context

The bid domain is **seven near-identical tables**: `bids_arsitek`, `bids_kontraktor`,
`bids_notaris`, `bids_interior`, `bids_structural`, `bids_mep`, `bids_project_manager`.
Together: **235 columns**, 7 indexes each, 7 model classes (426 LOC).

Of the 235 columns, **27 are universal** and **22 are role-specific**. **189 (80 %) are
exact duplicates.**

The duplication has already caused real incidents:

- `config/bids.php` exists as a "single source of truth" — and it is **wrong for 6 of
  7 roles** (defect B5).
- `ProjectController` carries **four** hand-maintained `match` ladders over role →
  model, role → FK column, role → project column, role → profile model.
- `PaymentVerificationService` carries **five** more (`:596-605`, `:609-618`,
  `:625-631`, `:650-658`, `:753-759`) — and one of them, `checkAndActivateBid`, **moves
  money**.
- `ProjectController` alone references the bid models **57 times**.
- The cross-table id-collision bug class: **profile ids are per-table and overlap**.
  Architect 42 and contractor 42 are different people. It has already produced a
  production incident — `FINAL-SWEEP.md` §4.8, where `PayoutDestinationService`'s memo
  was keyed by `"ModelClass:id"` but its *result* was keyed by the bare profile id, so a
  project was shown the **contractor's** bank details under the **architect's** role.
  The owner would have been told to pay the wrong person for the wrong stage.

**The dashboard is the clincher.** `ProjectController::index` is **320 lines** with a
**7-way branch** over bid relations for eager loading, a **7-way branch** of `withCount`
subqueries, a **7-way branch** of discovery-feed filters, a **7-way branch** of "my
projects" filters, and a 7-way branch in `getBids`, `submitBid`, `acceptBid`,
`declineBid` and `myBids`.

## Decision

**One `bids` table with a `bid_role` discriminator.**

```sql
CREATE TABLE bids (
    id                 bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id         bigint   NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    role               bid_role NOT NULL,
    bidder_user_id     bigint   NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    bidder_profile_id  bigint   NOT NULL,
    status             bid_status NOT NULL DEFAULT 'pending',
    payment_status     bid_payment_status NOT NULL DEFAULT 'unpaid',
    price              numeric(24,2) NOT NULL DEFAULT 0,
    ... 45 shared columns ...
    tax_estimate       numeric(24,2),   -- notaris
    fee_percentage     numeric(5,2),    -- notaris
    selected_services  jsonb,           -- notaris
    construction_method varchar(255),   -- kontraktor
    cost_breakdown     jsonb,           -- kontraktor
    warranty_months    int,             -- kontraktor
    workforce_count    int,             -- kontraktor
    equipment_owned    text,            -- kontraktor
    license_number     varchar(255),    -- structural, mep
    experience_years   int,             -- structural, mep
    technical_notes    text,            -- structural, mep
    interview_notes    text,            -- structural, mep
    style              varchar(255),    -- arsitek, interior
    CONSTRAINT bids_project_role_bidder_unique UNIQUE (project_id, role, bidder_user_id)
);
```

Three decisions inside that:

1. **`bidder_user_id` is the authoritative identity.** A user holds at most one profile
   per role, so `(role, user_id)` is functionally equivalent to `(role, profile_id)` —
   but `user_id` is *globally unique* and joins directly to `users`.
   `bidder_profile_id` is preserved **verbatim** for the audit trail and resolved through
   the role registry. **The per-table profile-id overlap is therefore structurally
   impossible to get wrong**, because no key in the new schema is a bare profile id.

2. **The role-specific columns stay as real nullable columns**, not a `jsonb` bag. Four
   are money (`tax_estimate`, `fee_percentage`) and two are read by the bid card
   (`selected_services`, `cost_breakdown`). A `jsonb` bag would make them unqueryable
   and un-typeable. The per-role overlays are typed in Go and marshalled into typed
   JSON columns.

3. **The seven wire keys are preserved.** The SPA reads `bids_arsitek`,
   `bids_kontraktor`, `bids_notaris`, `bids_interior`, `bids_structural`, `bids_mep` and
   `bids_project_manager` as separate top-level arrays in 40+ places. The Go serializer
   emits them from **one** query via an in-memory split. **The frontend does not change
   at all.**

**The migration sequence:** create the table → backfill from the seven (carrying
`bidder_user_id ← profile.user_id` and `bidder_profile_id ← the legacy id` verbatim) →
reconcile (row counts, per-column checksums, and an **identity reconciliation** that
counts bids whose profile has no user or whose user has a *different* profile in the
same role — currently 0) → dual-write → verify → drop the seven tables (or keep them as
**views** over `bids`, which is the more attractive end state) → switch the reads.

**The legacy unique indexes are keyed on the *profile* id; the new constraint is keyed
on the *user* id.** `arsiteks.user_id` and its siblings have only a **non-unique**
index today, so a user with two `arsiteks` rows could hold two bids under the legacy
rule and one under the new one. **Fix: make the profile tables' `user_id` unique** in
the PostgreSQL baseline. The pre-flight count is 0, so no data rewrite is needed.

## Consequences

### Positive

- **235 columns → 55.** The duplication is gone, not just hidden behind a helper.
- **The seven-way branch in `ProjectController::index` (320 lines) becomes a loop.**
- **The cross-table id-collision class is structurally impossible** — no key in the new
  schema is a bare profile id.
- **One `bid_status` enum** for all seven roles, replacing the mixed
  ENUM/varchar regime (ADR-0007).
- **The bid query is one index scan**, not seven, and the `bids` payload is produced
  from one typed struct per role.
- **The registry becomes a single Go map** instead of four `match` ladders in
  `ProjectController` and five in `PaymentVerificationService`.

### Negative

- **The backfill is the risky part.** 235 columns across seven tables, with three of
  them storing `status` as a `varchar` that must be cast to the new enum. The cast
  aborts the migration on an out-of-range value — which is the *desired* behaviour, and
  the pre-flight query names the offending row.
- **The legacy unique indexes cannot stay** once the constraint changes keying, so the
  drop order matters: they go when the legacy tables go, not before, because during the
  dual-write window the legacy index is the *operative* business rule.
- **The seven legacy tables become views or are dropped** — and any ad-hoc SQL,
  report or export that joins them directly must be updated. The `DetectDuplicateKeys`
  command's seven per-table queries become one grouped query.

### Neutral

- **`config/bids.php` becomes `spec/bids.yaml`**, and it generates the Go `RoleSpec`
  registry, the `bid_role` enum, the TypeScript role union and the pre-flight queries.
  Its `project_user_key` field is **corrected** at the same time (ADR-0015).
- **The `bids` table is the largest single schema change in the rewrite**, and it lands
  in the Postgres track (W4–W8) — before the Go slices that depend on it.
