# ADR-0013: The ledger reference vocabulary becomes a registry

- **Status:** Accepted
- **Date:** 2026-10-19
- **Deciders:** Davin Akmal Yasha

## Context

`project_budget_transactions` has a polymorphic key: `reference_model` (a varchar) and
`reference_id` (a bigint). It names the thing a ledger row is *about* — a bid, a
payment stage, an addendum, a material order, a change order, an external vendor, a
dispute.

**The live database contains the same payment written twice, under two spellings of the
same model:**

```
id 5619: reference_model = 'ProjectAddendum'            (short name)
id 5918: reference_model = 'App\Models\ProjectAddendum' (FQCN)
both:   project_id=14975, reference_id=934, transaction_type='payment', amount=5500000.00
```

The unique index is `budget_tx_reference_unique (project_id, reference_model,
reference_id, transaction_type)`. The two spellings **do not collide**, so the index
**cannot dedupe them**, and `paidTotalMoney()` — which sums every disbursement row —
counts the same Rp 5 500 000 payment **twice**. That project's escrow is understated by
Rp 5 500 000.

Three code paths write the reference, and they disagree:

| Writer | Spelling |
|---|---|
| `ProjectFinancialService.php:297-299` | normalises to the **FQCN** |
| `PaymentVerificationService.php:622-633` (`getRefModelName`) | the **short name** (`'BidArsitek'`, `'ProjectPaymentTermin'`, …) |
| `MaterialOrderController` | the **literal** `'MaterialOrder'` |

The `2026_08_25` normalisation migration did not fix it, and could not: its
`NOT EXISTS` guard refuses to rename the short-named row **precisely when the FQCN twin
already exists** — so the duplicate pair survives that migration *by design*.

The same shape appears in three more places:

- `bid_negotiation_logs.bid_type` — an Eloquent FQCN. `Relation::morphMap()` registers
  nine entries and **none of them is a bid model**, so the raw class name is stored.
- `project_addendums.recommended_bid_type` — a role name (`'notaris'`, `'structural'`).
- `project_disputes.payment_type` — a class name (`DisputeService.php:307` writes
  `get_class($payment)`).

And a **live enum mismatch**: `DisputeService` flips `status='refunded'` on an addendum
after writing the refund ledger row, but `project_addendums.status` has **no `refunded`
member** — so a dispute refund against an addendum is a hard MySQL error *after* the
money moved.

## Decision

**Replace every polymorphic model-name string with a `smallint` foreign key into a
registry table.**

```sql
CREATE TABLE ledger_reference_types (
    id             smallint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    type_key       varchar(64)  NOT NULL,
    fqcn           varchar(255) NOT NULL,
    legacy_aliases text[]       NOT NULL DEFAULT '{}',
    target_table   varchar(64)  NOT NULL,
    CONSTRAINT ledger_reference_types_type_key_key UNIQUE (type_key),
    CONSTRAINT ledger_reference_types_fqcn_key     UNIQUE (fqcn)
);
```

Fourteen seed rows, each carrying **every spelling the code has ever written** for that
model — the FQCN plus all its short-name aliases.

**The migration runs in one transaction, in four steps:**

1. **Normalise the spelling** via an explicit `CASE` over every known spelling. It is
   spelled out rather than derived from a join, because a join against `legacy_aliases`
   would silently skip a spelling present in the data but missing from the registry —
   and an unmapped row would keep its string and then fail the FK constraint *in the
   middle of a transaction*, with an error pointing at a column rather than at the
   spelling that caused it.
2. **Collapse the duplicate pairs**, keeping the **lowest id** — the ledger is an
   append-only audit trail, so the first write is the real event and the second is the
   duplicate. The discarded row's amount is added **nowhere**: it was never a separate
   movement of money, it was the same movement written twice.
3. **Add the typed columns and prove the mapping is total.** A `DO $$ … RAISE
   EXCEPTION` aborts the migration if any row has a `reference_model` and no
   `reference_type`.
4. **Swap the index and drop the varchars.**

> **PostgreSQL 15+ `UNIQUE NULLS NOT DISTINCT` is required, not optional — but
> it must be a PARTIAL index, not a table-level constraint.**
>
> The structural rows (`deposit`, `adjustment_down`) carry **no** reference, so
> `reference_type` and `reference_id` are NULL. Under the default NULLS-DISTINCT
> semantics every deposit row is mutually "unique" and the index protects
> nothing.
>
> **Corrected 2026-10-21.** The original wording here said
> `UNIQUE NULLS NOT DISTINCT (project_id, reference_type_id, reference_id,
> transaction_type)`, and that is a BUG: with all three reference columns
> NULL, every deposit and every `adjustment_down` row on a project is the SAME
> key, so **a project could receive exactly one deposit, ever** — and a
> deposit has to be repeatable (`docs/MONEY.md` §4.4).
>
> The index is therefore **partial**: `WHERE reference_id IS NOT NULL`, so the
> structural rows are outside the key and only movements that name WHAT they
> are about are deduplicated. `NULLS NOT DISTINCT` is still load-bearing there:
> it is what makes a *partially* populated reference key dedupe against
> another such row.

The same registry is used for `bid_negotiation_logs` (which has 0 rows today — but a
zero-row table today is a table with rows in six months) and for
`project_disputes.payment_type`. `project_addendums.recommended_bid_type` becomes a
`bid_role` enum.

**In Go, `Relation::morphMap` disappears.** It existed only so Eloquent could turn a
string back into a class. Go's exhaustive `switch` is compile-checked, so the class of
bug where a type is registered in one place and not another cannot recur.

## Consequences

### Positive

- **The live double-count is fixed, and the fix is provable.** The migration's
  reconciliation query must return zero rows afterwards, and `money:detect-duplicates`
  must be clean.
- **The double-charge guard actually works.** A `smallint` key cannot be spelled two
  ways.
- **`ALTER TYPE` is no longer needed for the reference vocabulary.** A new referenced
  model is one registry row.
- **The morphMap half-registration bug class is gone.** In Go it is a compile error.
- **The registry is self-documenting**: `legacy_aliases` records exactly which spellings
  existed and why, which is the forensic detail a future reader needs.

### Negative

- **The migration is irreversible in the sense that it cannot be re-run against a
  database that has already been migrated** without a guard. It is written to be
  idempotent-by-construction (the `CASE` is a no-op on already-normalised data, and the
  collapse is a no-op when no duplicates exist) and it is tested against both a
  populated and an empty database.
- **`smallint` caps the registry at 32 767 reference types.** That is four orders of
  magnitude beyond what this domain needs, but it is a hard ceiling.
- **The Go `switch` over reference types must be kept in sync with the registry.** It is
  generated from `spec/enums.yaml` like everything else, and the CI's
  `contract-freshness` job fails on any drift.

### Neutral

- **The registry keeps the FQCN** for provenance. It is the only record of which class
  the application believed it was talking to at the time — the same reason
  `bid_negotiation_logs.bid_type` is kept for one release as a forensic trail.
- **The `project_addendums` `refunded` enum gap is fixed in the same batch** — the
  value is added to the enum, and the refund path is corrected to use a column that
  exists.
