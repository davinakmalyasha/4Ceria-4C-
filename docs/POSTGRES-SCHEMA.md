# The PostgreSQL 17 Baseline

**Status:** Baseline, applied and verified · **Owner:** Davin Akmal Yasha
**Decisions:** ADR-0006 (PostgreSQL 17 is the target) · ADR-0007 (native enums) ·
ADR-0008 (collation per column family) · ADR-0013 (the ledger reference registry) ·
ADR-0014 (one `bids` table) · ADR-0015 (hired professionals are profile ids) ·
ADR-0020 (the escrow invariants live in the database)
**Migrations:** `db/postgres/migrations/` · **Enum manifest:** `spec/enums.yaml` ·
**Instrument:** `tools/db/inspect-legacy-schema.mjs`

> The Laravel application is the ORACLE and it is not modified by this work. The
> MySQL database keeps running. This document describes the TARGET schema and
> the reasoning behind it; nothing here changes the legacy application.

### 1.1 The headline numbers

| | Legacy (MySQL 9.6, live `4ceria`) | Baseline (PostgreSQL) | Δ |
|---|---:|---:|---:|
| Tables | 98 | **86** | −12 |
| Columns | 1 348 | **1 130** | −218 |
| Indexes (unique + plain) | 338 | **200** | −138 |
| Foreign keys | 161 | **161** | 0 |
| ENUM columns | 44 | **50** | +6 |
| ENUM types | 28 (derived) | **36** | +8 |
| JSON / jsonb columns | 59 | **36** | −23 |
| `numeric(24,2)` money columns | 83 | **47** | −36 |
| `timestamptz` columns | 251 | **227** | −24 |
| `citext` columns | 0 (the collation was implicit) | **6** | +6 |
| Identity columns | 90 `AUTO_INCREMENT` | **82** `GENERATED BY DEFAULT AS IDENTITY` | −8 |

The column, index, JSON and money counts fall because **seven near-identical bid
tables become one** (235 columns → 55). Everything else is carried over.

The index count falls for two reasons: the seven bid tables' indexes collapse
into one table's eight, and MySQL's **108 explicit foreign-key backing
indexes** are not reproduced — PostgreSQL creates the index a foreign key
needs, by itself, and a second copy of it would be a redundant index (the
`FINAL-SWEEP.md` §2 finding that three of the legacy indexes were exact
duplicates applies here too).

## 2. The decisions

### 2.1 Types

| Legacy | Baseline | Note |
|---|---|---|
| `bigint unsigned AUTO_INCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY` | Not `serial`: `serial` is a sequence with a default and an ownership quirk; `GENERATED BY DEFAULT AS IDENTITY` is the modern form and allows an explicit id on insert. |
| `bigint unsigned` | `bigint` | Unsigned-ness is meaningless for a currency and makes a negative refund unrepresentable. The four `int unsigned` columns that survive are `jobs.*` and `jobs` stays in MySQL. |
| `decimal(24,2)` | `numeric(24,2)` | Exact base-10. `SUM()` over the ledger is exact. **Never `float`, never `double precision`.** |
| `decimal(15,2)`, `decimal(18,2)`, `decimal(10,7)`, `decimal(5,2)` | `numeric(p,s)` unchanged | These are quantities, coordinates and percentages, not money. |
| `json` | `jsonb` | 36 columns. `jsonb` gives GIN-indexable operators that the nine `whereJsonContains` sites need. |
| `timestamp`, `datetime` | `timestamptz` | 227 columns. |
| `tinyint(1)` | `boolean` | 17 columns. |
| `varchar(n)` | `text` + `CHECK (char_length(col) <= n)` | 292 length constraints. MySQL rejected an over-long value under strict mode; `text` would not. |
| `text`, `mediumtext`, `longtext` | `text` | |
| `enum(...)` | a native `CREATE TYPE ... AS ENUM` | 36 types. See §3. |

**The only column that was renamed** is `users.Deskripsi` → `users.deskripsi`.
MySQL column names are case-insensitive; PostgreSQL folds unquoted identifiers
to lower case, so keeping the capital `D` would mean quoting it everywhere.
Nothing in the application reads that column — every other `deskripsi` in the
codebase is on a **profile** table.

**`created_at` / `updated_at` became `NOT NULL DEFAULT now()`.** The legacy
columns are nullable with no default, because that is what Laravel 9 produced.
Every writer sets them and the live data contains no NULL in either, so the
NOT NULL is a guarantee rather than a change.

### 2.2 The escrow ledger

`project_budget_transactions` is the escrow's only source of truth, and three
things about it changed.

**(a) The reference became a registry key.** `reference_model` was a VARCHAR
holding an Eloquent class name, and the live database held the same Rp 5 500 000
payment written twice:

```
id 5619  reference_model = 'ProjectAddendum'
id 5918  reference_model = 'App\Models\ProjectAddendum'
both:    project_id=14975, reference_id=934, transaction_type='payment', amount=5500000.00
```

The unique index that makes the ledger idempotent is keyed on the reference, so
two spellings do not collide and the escrow is understated by exactly
Rp 5 500 000 (REWRITE-PLAN defect B4). `reference_model` is now
`reference_type_id smallint REFERENCES ledger_reference_types(id)`, and the
registry carries every spelling that was ever written in `legacy_aliases`.

**(b) The invariant moved into the database.** `escrow.record_movement()` is a
`SECURITY DEFINER` function and the ONLY writer. The application role has no
`INSERT`, `UPDATE` or `DELETE` on the table — verified:

```
schema_usage | can_call_record | can_insert_ledger | can_read_ledger
t            | t               | f                 | t
```

The function performs, in one transaction and one `FOR UPDATE` lock: the
affordability check, the atomic dedupe guard (`ON CONFLICT … DO NOTHING
RETURNING id`), and the ceiling movement — in that order, because in the PHP
original the ceiling was decremented first and a duplicate could commit a
ceiling change with no ledger row (MONEY.md §5).

**(c) The dedupe key.** The requirement is a `UNIQUE NULLS NOT DISTINCT`
constraint "so a nullable reference still deduplicates". The baseline implements
it as:

```sql
CREATE UNIQUE INDEX budget_tx_reference_unique
    ON project_budget_transactions (project_id, reference_type_id, reference_id, transaction_type)
    NULLS NOT DISTINCT
    WHERE reference_id IS NOT NULL;
```

**It is a partial index, and a plain table-level constraint would be a bug.**
A table-level `UNIQUE NULLS NOT DISTINCT (project_id, reference_type_id,
reference_id, transaction_type)` treats every structural row — every `deposit`
and every `adjustment_down`, which carry no reference — as the *same* key,
because all three reference columns are NULL. A project would then be able to
receive exactly **one** deposit, ever. A deposit must be repeatable
(MONEY.md §4.4), so the structural rows are excluded from the key and only
movements that name *what they are about* are deduplicated. `NULLS NOT
DISTINCT` is still load-bearing: it is what makes a row whose reference key is
only *partially* populated still dedupe against another such row, where the
default NULLS-DISTINCT semantics would silently stop the guard working.

**Two deviations from ADR-0020's sketch, both deliberate:**

1. ADR-0020's sketch returns `available` computed **before** the insert. A
   caller that trusted it would believe the escrow was unchanged after it moved
   the money. The baseline recomputes the outflow after the insert.
2. ADR-0020's sketch declares `p_reference_type ledger_ref_type` — a second
   enum vocabulary for the reference. ADR-0013 supersedes it with the
   `smallint` registry, which is what the baseline uses.

**The four dropped columns.** `category`, `type`, `status` and `description`
existed on the legacy ledger table and were never written by anything: they
are not in `ProjectBudgetTransaction::$fillable` and no code path sets them.

**`actor_user_id` deliberately has NO foreign key.** The ledger is an immutable
historical record; deleting a user must not erase the fact that they moved the
money. The legacy schema made the same choice.

### 2.3 The unified `bids` table

Seven tables, 235 columns, 185 of them exact duplicates, become one table with
a `role` discriminator.

**The status enum is the union of the seven.** Four of the legacy status
columns are MySQL ENUMs with the same twelve values in the same order; three
(`bids_mep`, `bids_project_manager`, `bids_structural`) are `VARCHAR(255)` with
no type constraint at all. The same controller code paths write the same twelve
values to all seven tables, so the union is the same twelve values and the
three varchar columns are **gaining** a type they never had.

**Which legacy table maps to which row shape:**

| Legacy table | `role` | Profile column | Role-specific columns it owned |
|---|---|---|---|
| `bids_arsitek` | `arsitek` | `arsitek_id` | `style`, `proposed_team` |
| `bids_kontraktor` | `kontraktor` | `kontraktor_id` | `construction_method`, `cost_breakdown`, `workforce_count`, `equipment_owned`, `warranty_months`, `payment_preference`, `proposed_team` |
| `bids_notaris` | `notaris` | `notaris_id` | `tax_estimate`, `fee_percentage`, `selected_services` |
| `bids_interior` | `interior` | `interior_id` | `style` |
| `bids_structural` | `structural` | `structural_id` | `license_number`, `experience_years`, `technical_notes`, `interview_notes` |
| `bids_mep` | `mep` | `mep_id` | `license_number`, `experience_years`, `technical_notes`, `interview_notes` |
| `bids_project_manager` | `project_manager` | `pm_id` | — |

The fifteen role-specific columns stay **real nullable columns**, not a `jsonb`
bag: four are money (`tax_estimate`, `fee_percentage` and the shared money
columns) and two are read by the bid card (`selected_services`,
`cost_breakdown`).

**The identity.** `bidder_user_id` is the authoritative identity — globally
unique, joins straight to `users`. `bidder_profile_id` is the legacy profile id
preserved **verbatim** for the audit trail. The seven legacy per-role columns
are kept as real nullable columns with real foreign keys, and a CHECK
constraint ties them together:

```
the column whose role matches `role` must equal `bidder_profile_id`,
and the other six must be NULL
```

**The uniqueness rule changed keying.** The legacy unique indexes were
`(project_id, <role>_id)` — keyed on the *profile* id. The new one is
`(project_id, role, bidder_user_id)` — keyed on the *user* id. Those coincide
only because a user holds at most one profile per role, which the legacy schema
did **not** enforce (it indexed `<table>.user_id` non-uniquely). Every profile
table therefore gains `UNIQUE (user_id)`; the pre-flight count of duplicate
`user_id`s is **0** in all nine profile tables, so no data changes.

**Three legacy inconsistencies were resolved, and they are worth knowing about:**

| Column | Legacy | Baseline | Why |
|---|---|---|---|
| `estimated_duration` | `int` in five tables, `varchar(255)` in `bids_interior` and `bids_notaris` | `integer` | The application validates it as `nullable\|integer` and always writes an integer (`ProjectController:866`). The two varchar declarations are schema drift. The live values are `5, 4, 7, 30, 3`. |
| `duration_unit` | `varchar(255)` in five tables, `varchar(50)` in two, `NOT NULL DEFAULT 'weeks'` for PM bids | `text`, nullable | The application writes `duration_unit ?: 'weeks'` at bid creation (`ProjectController:914`), so the database default was belt-and-braces. The unified column cannot have a role-specific default. |
| `proposal` | nullable in four tables, `NOT NULL` in three | `text`, nullable | The four nullable tables hold rows with a NULL proposal. The three NOT NULL tables were the varchar-status ones. |
| `fee_type` | `varchar(50)` in six tables, `varchar(255)` for PM bids | `text`, length ≤ 255 | The loosest legacy limit wins, so the unified table never rejects a value the legacy schema accepted. |

### 2.4 `projects.selected_*` — every one of them is a profile id

Seven columns, seven profile tables, seven foreign keys:

| Column | References | Was a foreign key in MySQL? |
|---|---|---|
| `selected_arsitek_id` | `arsiteks(id)` | **No** |
| `selected_kontraktor_id` | `kontraktors(id)` | **No** |
| `selected_notaris_id` | `notaris_profiles(id)` | **No** |
| `selected_interior_id` | `interior_profiles(id)` | **No** |
| `pm_id` | `project_managers(id)` | **No** |
| `structural_id` | `structural_engineers(id)` | **No** |
| `mep_id` | `mep_engineers(id)` | **No** |

The legacy schema declared **none** of them — they were bare unsigned bigints
with a plain index — and it declared `pm_id` as the PM's **user** id while the
other six held profile ids. The 2026-10-21 migration made `pm_id` a profile id
too (ADR-0015), so there is now one convention and the database enforces it.
The live data confirms it: project 14975 has `pm_id = 831`, and
`project_managers.id = 831` has `user_id = 31689` — the PM's *user* id is one
join away and the *profile* id is what the column holds.

`projects.owner_id` is carried over verbatim and left unconstrained: nothing
reads it (the API resource emits `user_id` under the name `owner_id`), and the
legacy schema declared no foreign key on it either.

## 3. Enums

**`spec/enums.yaml` is generated, never transcribed.** `tools/db/inspect-legacy-schema.mjs`
reads the live `information_schema.COLUMNS` and emits the file; `--check` fails
if the committed file differs from what the database says.

| | Count |
|---|---:|
| Legacy ENUM columns | 44 |
| Types derived from them | 28 (three column names carry several distinct value lists — `status` appears on thirteen tables — so each list gets its own type; nine column names carry one list each and are shared) |
| Types introduced by the rewrite | 8 |
| **Total types in the baseline** | **36** |
| ENUM columns in the baseline | 50 (the 44 legacy ones plus 6 that were VARCHARs and are now enums) |

**The value ORDER is MySQL's.** PostgreSQL's `pg_enum` sorts by
`enumsortorder`, so a reordered list is a behaviour difference, not a cosmetic
one. `pg_enum.enumsortorder` is assigned by the order of the `CREATE TYPE`
statement, and the baseline emits the values in exactly the order
`information_schema` reports them.

**The eight rewrite-introduced types** are the VARCHAR state machines ADR-0007
lists, plus the role discriminator:

| Type | Values | Replaces |
|---|---|---|
| `bid_role` | arsitek, kontraktor, notaris, interior, structural, mep, project_manager | the seven per-role bid id columns; `project_addendums.recommended_bid_type` |
| `bid_payment_status` | unpaid, pending, verifying, paid, refunded | `bids_*.payment_status` on all seven tables |
| `payment_termin_status` | locked, pending, invoice_sent, verifying, accepted, paid, void | `project_payment_termins.status` (the most money-critical state machine in the app) |
| `project_planning_status` | draft, proposed, approved, pm_verified | `projects.planning_status` |
| `project_construction_brief_status` | draft, pending_review, revision_requested, approved | `projects.construction_brief_status` |
| `project_walkthrough_status` | in_progress, completed | `projects.walkthrough_status` |
| `dispute_status` | open, resolved, dismissed, withdrawn | `project_disputes.status` |
| `dispute_resolution` | dismiss, release_payment, record_refund, terminate_project, custom | `project_disputes.resolution` |

`bid_role`'s value order is the one in `config/bids.php` and in
`project_sub_professionals.parent_role`, which carry the same seven values in
the same order. `project_external_vendors.phase_role` carries the same seven
values in a **different** order (project_manager before structural and mep), and
it keeps its own type — the two legacy orderings are preserved verbatim rather
than reconciled, because reconciling them would be a silent change to two
existing enums.

## 4. Collation — the decision, per column family

MySQL's default collation is `utf8mb4_0900_ai_ci`: **case-insensitive** and
**accent-insensitive**. PostgreSQL's default is case-sensitive and
accent-sensitive. The baseline is created against a database with
`LC_COLLATE=C LC_CTYPE=C`, so every comparison that the schema does not
explicitly mark as case-insensitive is **byte-exact**. That is the strictest
reading, and it makes an accidental case-insensitive match impossible.

| Family | Columns | Treatment | Why |
|---|---|---|---|
| **Authentication identifiers** | `users.email`, `password_reset_tokens.email`, `personal_access_tokens.token` | **`citext`** | Case-insensitivity is a correctness requirement here, not an accident. `citext` keeps the equality operator's semantics unchanged, so a query does not have to change. |
| **Public share / invite tokens** | `projects.share_token`, `users.unique_code` | **`citext`** | A token is a secret, and secrets are case-insensitive by convention. `users.unique_code` is a six-character code from an UPPERCASE alphabet, and the firm service already uppercases the query (`FirmMemberService:24`) — so citext is belt-and-braces rather than load-bearing, but it costs nothing and preserves MySQL's uniqueness semantics exactly. |
| **Human-facing unique names** | `users.username` | **`citext`** | Typed by humans. Two humans typing `Budi` and `budi` must not create two accounts. |
| **Enum / status / type columns** | all 36 enum types, `transaction_type`, `role_type`, `verification_status`, `phase_role`, `owner_role` | **native enum — case-sensitive** | Machine-written from a fixed vocabulary. Case-insensitivity here would *hide* a typo (`'Paid'` matching `'paid'`) — precisely the failure mode `AGENTS.md` trap #8 warns about. |
| **Free-text content** | `proposal`, `notes`, `description`, `review` text | **case-sensitive, the default** | Human text. Case-insensitive search over free text is a feature request, and `ILIKE` is available when it is wanted. |
| **JSON payloads** | the 36 `jsonb` columns | **case-sensitive, the default** | Structured data, matched exactly. |
| **Search columns** | `users.name`, `projects.title`, `house.name`, `materials.name`, `suppliers.store_name`, `project_milestones.title` | **`text` + a GIN trigram index on `lower(col)`** | See §4.2. |
| **Machine vocabulary** | `permissions.name`, `roles.name`, `notification_preferences.type`, `notification_preferences.channel`, `user_channels.channel`, `contractor_subspecialties.slug`, `material_orders.whatsapp_order_id`, `push_subscriptions.endpoint` | **case-sensitive, the default** | Written by code from a fixed vocabulary, and compared exactly. A case-insensitive comparison would hide a typo. `push_subscriptions.endpoint` is a URL, and a URL's path IS case-sensitive — MySQL's collation could conflate two genuinely different endpoints. |
| **Free-text personal data** | `users.name`, `users.firm_name`, `arsiteks.nama`, `kontraktors.nama`, … | **case-sensitive, the default** | They are compared for equality only where the application already normalises. The SEARCH over them is the search family above. |

`citext` is applied to **six columns**. It is not applied to a whole table, and
it is not applied to a whole family of "names" — the search family uses a
functional index instead, because a search needs `ILIKE`-style matching across
a substring, which `citext` does not provide (`citext` changes `=`, not `LIKE`).

### 4.1 Where MySQL's case-insensitivity was load-bearing

These are the places that break **silently** — no type error, no lint warning,
no failed test, until a test exists:

1. **Login.** `AuthController:38` is `User::where('email', $request->email)`.
   The *stored* value is lowercased by the registration path
   (`AuthController:81`); the *looked-up* value is the raw request. Under
   MySQL's case-insensitive collation that mismatch was invisible. Under
   PostgreSQL's default it is a 404 on every differently-cased login.
   → `users.email` is `citext`.

2. **Every Sanctum token lookup.** `personal_access_tokens.token` is compared
   on every authenticated request. → `citext`.

3. **The public brief link.** `ProjectController:3002` is
   `Project::where('share_token', $token)`. The token is `bin2hex(random_bytes(12))`
   — lowercase hex — so the stored value is always lowercase, but a link
   pasted with the case changed would 404. → `citext`.

4. **The firm invite code.** `FirmMemberService:24` and
   `FirmMemberController:166` look a professional up by `users.unique_code`.
   Both already `strtoupper()` the query, so the lookup is
   collation-independent — **this one is not load-bearing**, and the baseline
   says so. `citext` is applied anyway because it costs nothing.

5. **Ten `LIKE '%term%'` searches.** Under MySQL, `LIKE` was case-insensitive
   *and* accent-insensitive. Under PostgreSQL, `LIKE` is neither. These are
   the searches that will silently return FEWER rows:

| Site | Column |
|---|---|
| `AdminDashboardController:60,62` | `users.name` |
| `AdminDashboardController:90,92` | `projects.title`, `users.name` |
| `AdminDashboardController:110,112` | `projects.title` |
| `AdminUserController:19` | `users.name` |
| `HouseController:38` | `house.name` |
| `MaterialController:77,102` | `materials.name` |
| `SupplierController:43` | `suppliers.store_name` |
| `FirmMemberController:167`, `FirmMemberService:25` | `users.name` |
| `ProjectDailyLogController:56`, `ProjectMilestoneController:55,158` | `project_milestones.title` |

   → the rule for the port is **`lower(col) LIKE lower(?)`**, and the index is
   built on the same expression so the index and the query cannot drift apart.
   The index is a **GIN trigram** index because every one of these searches is
   an *infix* match and a b-tree cannot serve one.

   That rule is load-bearing and it was measured, not asserted. With 20 000
   rows in `users` and one matching row:

   ```
   EXPLAIN SELECT id FROM users WHERE lower(name) LIKE lower('%zqxjkw%');
     Bitmap Heap Scan on users
       ->  Bitmap Index Scan on users_name_search_idx

   EXPLAIN SELECT id FROM users WHERE name LIKE '%zqxjkw%');
     Seq Scan on users
       Filter: (name ~~ '%zqxjkw%'::text)
   ```

   The second form — the one that looks natural — does not use the index at
   all.

### 4.2 What C costs: `ß` and the accents

MySQL's `utf8mb4_0900_ai_ci` treats `ß` = `ss` and strips accents.
PostgreSQL's `C` collation does neither. Three consequences, stated plainly:

1. **Accent-insensitive search is NOT reproduced.** Under MySQL, `LIKE '%cafe%'`
   matched `café`. Under PostgreSQL it does not. This affects all ten search
   sites in §4.1. Reproducing it needs the `unaccent` extension and a
   functional index on `unaccent(col)` — `unaccent(text)` is only STABLE, so
   the indexable form is `unaccent('unaccent'::regdictionary, col)`. That is a
   deliberate non-goal of the baseline: it is a **search-recall** difference, it
   belongs to the parity phase, and it is not a schema-correctness issue. It is
   recorded here so nobody discovers it in production.
2. **`ß` = `ss` is NOT reproduced.** A name search for `weiss` did not find
   `Weiß` under MySQL and will not under PostgreSQL. `citext` folds case using
   the database collation, and under `LC_CTYPE=C` that fold is ASCII-only — so
   a `citext` column containing non-ASCII characters folds only their ASCII
   part. Every `citext` column in this schema holds an ASCII-only value in
   practice (email, username, a 6-character code from
   `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, a hex token, a sha256 hash).
3. **The `C` collation is also the reason a `LIKE` on a non-ASCII name sorts
   differently.** Under MySQL's `ai_ci` the sort order was accent- and
   case-insensitive; under `C` it is byte order. The public professional
   directory sorts by name in several places
   (`FirmMemberService:27` orders by `name`), so the ORDER of a listing can
   differ from the legacy application. This is a **visible** difference, unlike
   the case-insensitive match, and it is listed here for the parity phase to
   decide. It was not reproduced by adding a non-`C` collation to the column,
   because a case-insensitive UNIQUE index on a `citext` column is already the
   mechanism ADR-0008 chose, and mixing the two would reintroduce the
   ambiguity the ADR removed.

## 5. What is deliberately NOT migrated

### 5.1 Tables

| Legacy table | Why |
|---|---|
| `migrations` | Laravel's migration ledger. The PostgreSQL baseline has its own (goose). |
| `jobs`, `job_batches`, `failed_jobs` | Laravel's queue tables. The rewrite runs its own queue; MySQL keeps the Laravel one. |
| `cache`, `cache_locks` | Laravel's cache store. The rewrite uses Redis. |
| `sessions` | Laravel's session store. The rewrite uses Redis / cookie sessions. |

**`users`, `password_reset_tokens` and `personal_access_tokens` ARE in the
baseline** even though ADR-0018 keeps them in MySQL for the whole transition.
They are in the baseline because the port needs them eventually and because
the Eloquent model reads `users` on every authenticated request; ADR-0018 is an
*ownership* decision (which engine writes them today), not a schema decision.

### 5.2 Tables that were REPLACED rather than copied

## 7. The instrument

`tools/db/inspect-legacy-schema.mjs` is the gate that keeps the port honest.
It uses the `mysql` and `psql` command-line clients, so it needs no driver
package and runs in CI with nothing but the database images.

| Mode | What it does |
|---|---|
| *(default)* | Reads the live MySQL schema and writes `spec/enums.yaml` and `spec/legacy-schema.json` (the column-level inventory of all 98 tables). |
| `--check` | Writes nothing; exits 1 if the committed artefacts differ from what the live database says. This is the CI freshness gate. |
| `--verify-enums` | Compares `spec/enums.yaml` against the live MySQL **and** a live PostgreSQL, value by value **and in order**. |
| `--diff` | Diffs the legacy schema against the PostgreSQL baseline and reports every missing table, column, enum type, enum value and foreign key. Also checks that every table and column the 81 Eloquent models touch exists. |
| `--diff --pg-dsn <dsn>` | The same, against a **live** PostgreSQL instead of the migration files. |

The diff knows about the deliberate transformations (the seven bid tables
folding into one, the four renamed reference columns, the four dropped dead
columns, the seven Laravel framework tables) so that it reports only what is
genuinely missing. Anything not on that list is a failure.

## 8. What was verified, and what was not

### 8.1 Verified

| Check | Result |
|---|---|
| All 8 migrations applied to a **from-scratch** PostgreSQL database | **PASS** — no errors. |
| The PostgreSQL available locally | PostgreSQL **18.6** on `127.0.0.1:5432` (Laragon). **Not 17.** |
| The database was created with `LC_COLLATE=C LC_CTYPE=C` | **PASS** — `datcollate = C`, `datctype = C`. |
| `--diff --pg-dsn` against that live database | **CLEAN** — 0 missing tables, 0 missing columns, 0 missing enum types, 0 missing enum values, 0 missing foreign keys. |
| `--verify-enums` against MySQL **and** PostgreSQL | **PASSED** — all 36 types, same values, same order, on both sides. |
| Every table and column the 81 Eloquent models touch | **PASS** — 0 missing tables, 0 missing columns. |
| The escrow function's invariants, executed | **PASS** — deposit raises the ceiling and is repeatable; the same payment twice is one row and one ceiling move; a `platform_fee` may share the payment's reference; an unaffordable payment is refused with `insufficient_funds`; a refund is negative, references the dispute and reverses the payment; a positive refund is refused by `pbt_amount_sign`. |
| The privileges | **PASS** — `app_rw` can call `record_movement`, can read the ledger, and **cannot** insert into it. |
| The `bids` invariants, executed | **PASS** — a bid whose role and profile column disagree is refused; a bid whose `bidder_profile_id` does not match its role column is refused; a second bid from the same professional on the same project is refused; a project referencing a non-existent profile is refused. |
| The GIN trigram search indexes | **PASS** — with 20 000 rows and one match, `lower(name) LIKE lower('%zqxjkw%')` produces a **Bitmap Index Scan on `users_name_search_idx`**, and the un-folded form `name LIKE '%zqxjkw%'` produces a **Seq Scan**. The index and the rule are matched, and the rule is not optional. |
| The MySQL database | **Read-only.** No `DROP`, no `migrate`, no writes. The only database created or dropped was the scratch database `4ceria_pgcheck`. |

### 8.2 NOT verified — the honest gaps

1. **PostgreSQL 17 was not available.** The local server is **18.6**. Nothing
   in this baseline uses a feature newer than PostgreSQL 15
   (`UNIQUE NULLS NOT DISTINCT` is PG 15+), so 18.6 accepting it does not
   prove 17 does — but it is not the same proof. **The baseline must be applied
   to a PostgreSQL 17 instance before it is called final.** The features used:
   `citext` (9.1), `pg_trgm` (9.1), `btree_gin` (9.4), `GENERATED BY DEFAULT
   AS IDENTITY` (10), `NULLS NOT DISTINCT` on an index (15), `jsonb` (9.4),
   `timestamptz` (8.1), `ON CONFLICT … DO NOTHING RETURNING` (9.5).
2. **No data was migrated.** The baseline was applied to an EMPTY database and
   its constraints were exercised with hand-written fixtures. The ETL, the
   backfill, the duplicate collapse and the reconciliation query are **not**
   part of this work and are not verified.
3. **The `SECURITY DEFINER` ownership was not verified in production.** The
   function is owned by the migration role (`postgres` locally). In production
   it must be owned by a dedicated no-LOGIN role that is not `app_rw`, or the
   privilege model collapses.
4. **No round-trip.** The migrations are forward-only, and a `down` migration
   was deliberately not written — the PostgreSQL schema is the target, not a
   reversible copy of MySQL. The MySQL side remains the rollback mirror
   (REWRITE-PLAN §4.2, invariant 3).
5. **The `pg_trgm` search indexes were verified for USE, not benchmarked for
   throughput.** The planner was shown to use them for the `lower(col) LIKE
   lower(?)` form and to ignore them for the un-folded form (§4.1). No load
   test was run, and the six other search columns were not individually
   re-planned. The index expressions are `lower(col)`; the port's queries must
   use the same expression or the index is not used. That is a port-side
   obligation, not a schema one, and it is stated in §4.1.
6. **The `citext` ASCII-only folding** under `LC_CTYPE=C` was reasoned about,
   not fuzzed. Every `citext` column holds an ASCII-only value in practice,
   but a non-ASCII email would fold only its ASCII part.
7. **The Windows-hosted PostgreSQL 18.6 was used, not a Linux container.**
   The behaviour exercised here is all standard SQL and is not
   platform-dependent, but the CI image is `postgres:17` on Linux and the
   first run there is still outstanding.

## 9. Things the baseline found that the rewrite plan does not say

1. **ADR-0006 claims 250 `timestamp` columns need `ON UPDATE CURRENT_TIMESTAMP`
   handling. There are ZERO.** `information_schema.columns.extra` contains no
   `on update CURRENT_TIMESTAMP` for any of the 1 348 columns, and the only
   `DEFAULT CURRENT_TIMESTAMP` in the whole schema is `failed_jobs.failed_at` —
   a Laravel table that stays in MySQL. The legacy schema has no
   auto-updating timestamp column at all: `updated_at` is written by Eloquent.
   The "250 columns need a trigger or an explicit write" consequence in
   ADR-0006 does not exist, and no trigger is created here.

2. **ADR-0006 says "the 4 unsigned columns become `bigint` with a
   `CHECK (col >= 0)`".** The four `int unsigned` columns are `jobs.attempts`,
   `jobs.reserved_at`, `jobs.available_at` and `jobs.created_at` — all in
   `jobs`, which is a Laravel framework table that stays in MySQL. There is
   nothing to convert.

3. **ADR-0006 says "24 `tinyint(1)` columns become `boolean`". There are 22,
   and only 17 survive** — the six `is_recommended` columns on the legacy bid
   tables (all but `bids_project_manager`, which never had one) collapse into
   one.

4. **ADR-0006 says "82 money columns". There are 83** `decimal(24,2)`
   columns, and **47** in the baseline. The `83 → 47` collapse is the seven bid
   tables' six money columns each (42) becoming six.

5. **ADR-0014 says the unified `bids` table has 55 columns. It has 55 — but
   the composition differs from the ADR's sketch.** The ADR's sketch has
   `bidder_profile_id` and no per-role profile columns, with the seven role
   columns implied. The baseline keeps **both**: the seven legacy `<role>_id`
   columns (so that every column of the seven legacy tables is preserved, with
   a real foreign key) **and** `bidder_profile_id` (ADR-0014's verbatim audit
   trail), tied together by a CHECK constraint. That is 55 columns too, and it
   satisfies both readings.

6. **`bids_interior.estimated_duration` and `bids_notaris.estimated_duration`
   are `varchar(255)` while their five siblings are `int`.** Nothing in the
   application writes a non-numeric duration — it validates
   `nullable|integer` — so the two varchar declarations are drift. The baseline
   uses `integer` and says so.

7. **`bids_interior.estimated_duration` was missed by the schema:verify
   tooling.** It is a `varchar` on a column that is `int` on six siblings, and
   it is a `char_length`-invisible drift. It is the kind of thing the
   column-level inventory exists to catch.

8. **`users.Deskripsi` has a capital D.** MySQL column names are
   case-insensitive so it was invisible; PostgreSQL folds unquoted identifiers
   to lower case, so keeping it would mean quoting it in every query. Nothing
   reads it.

9. **`rooms.desc` is a PostgreSQL reserved word** (`desc` is the ordering
   direction). It is quoted as `"desc"` in the baseline. It is the only
   reserved word among the 1 348 column names.

10. **`project_addendums.status` has no `refunded` member**, so a dispute
    refund against an addendum is a hard error *after* the money moved
    (ADR-0013 records this). The baseline carries the legacy enum unchanged —
    the enum vocabulary is generated from the live database — so **the gap is
    still open** and is listed here rather than silently fixed, because adding
    a value to a generated enum by hand would break the generation contract.
    It needs its own migration in the rewrite track, with the ADR-0007
    "one migration per added value" rule.

11. **`project_external_vendors.phase_role` and
    `project_sub_professionals.parent_role` carry the same seven roles in
    DIFFERENT orders** (`phase_role` puts `project_manager` before `structural`
    and `mep`; `parent_role` does not). Both are preserved verbatim as
    separate types. The canonical order for the new `bid_role` is the one in
    `config/bids.php`, which matches `parent_role`.

12. **ADR-0013 says the registry has "fourteen seed rows".** Thirteen of them
    have a live writer in the legacy code. The fourteenth (`change_order`) is
    reserved by ADR-0013's own prose, which lists a change order among the
    things a ledger row can be about, but no code path references one: a
    change order's payment is booked against its payment stage. The baseline
    seeds all fourteen, because the ADR says fourteen, and the row's
    `legacy_aliases` array records that it has no writer yet.

13. **`Reference::morphMap()` registers nine entries and NONE of them is a bid
    model** (ADR-0013 says this). So `bid_negotiation_logs.bid_type` stored a
    raw class name — and the registry replaces it with `bid_type_id`. The
    table has **0 rows** today. It is still worth the registry key: a
    zero-row table today is a table with rows in six months, and this is the
    one place where the ledger's own defect class was still live.

14. **The `users.unique_code` firm-invite lookup is NOT collation-dependent.**
    `FirmMemberService:24` and `FirmMemberController:166` both
    `strtoupper()` the query before matching, and the generator only produces
    uppercase codes. ADR-0008 lists this column among the ones whose
    case-insensitivity was load-bearing ("firm invites stop resolving"); the
    code says otherwise. `citext` is applied anyway — it is harmless and it
    preserves MySQL's uniqueness semantics exactly — but the baseline does not
    claim it is load-bearing.

15. **The `projects.owner_id` column is vestigial.** The API resource emits
    `user_id` under the name `owner_id`, `ProjectFinancialService:170` aliases
    `projects.user_id as owner_id`, and nothing reads the column itself. It is
    carried over verbatim and left unconstrained.

16. **The ledger's "ceiling is `SUM(deposit) - SUM(adjustment_down)`" framing
    and the seeded data do not agree.** MONEY.md §3 is normative and says the
    ceiling is `projects.budget` and that `deposit`/`adjustment_down` MOVE it;
    the baseline implements exactly that. The seeded dev data does not
    corroborate the equivalent formulation: project 14975 has
    `budget = 5 000 000 000` and **no opening `deposit` row** at all, so
    `SUM(deposit) - SUM(adjustment_down)` is 0 for it. The opening-budget row
    is only written on some creation paths (`ProjectController:417` writes it
    directly rather than through `deductBudget`). The baseline therefore
    treats `projects.budget` as the ceiling of record and the ledger as the
    outflow of record, and it does **not** try to derive one from the other.

17. **`finance` is not a word MySQL and PostgreSQL agree on.** MySQL 8.0.30+
    and PostgreSQL both reserve `FINANCE`, but the legacy schema has no such
    column — this is noted only because a future migration must not name a
    column `finance` unquoted in either engine.

## 10. How to apply and verify the baseline

```bash
# Create the target database with the C collation.
createdb -T template0 --lc-collate=C --lc-ctype=C --encoding=UTF8 "4ceria_pgcheck"

# Apply, in order.
for f in db/postgres/migrations/000*.sql; do psql -v ON_ERROR_STOP=1 -d "4ceria_pgcheck" -f "$f"; done

# Prove it against the live MySQL schema AND the live PostgreSQL.
node tools/db/inspect-legacy-schema.mjs --diff --pg-dsn "postgresql://postgres@127.0.0.1:5432/4ceria_pgcheck"
node tools/db/inspect-legacy-schema.mjs --verify-enums --pg-dsn "postgresql://postgres@127.0.0.1:5432/4ceria_pgcheck"

# CI freshness gate: the committed artefacts must match the live database.
node tools/db/inspect-legacy-schema.mjs --check
```
